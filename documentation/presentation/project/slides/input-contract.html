Every export states how to build its input

preprocessing.json next to the exported model, also in the ONNX metadata. Detection tutorial run:

{
  "input_contract_version": "2",
  "input_color_order": "BGR",
  "input_resize": "keep_ratio",
  "input_size": "512",
  "input_interpolation": "linear",
  "input_padding_value": "0",
  "input_padding_placement": "centred",
  "input_tile_scale": "none",
  "input_tile_overlap": "none",
  "input_layout": "NCHW",
  "input_value_range": "0-255"
}

The export refuses an input it cannot describe; a test rebuilds the inputs from this file alone, pixel for pixel.

The three resizes of a 640 x 359 photo for an input of 256. Photo: COCO 2017 validation image 288882, Flickr, CC BY 2.0.

A server that feeds the model does not have to guess the preprocessing: the input contract travels with the model. Every export writes it into the metadata of model.onnx and as preprocessing.json next to both formats. On the left, the file of the detection tutorial run, built by the export code from the run: decode the photo in BGR as OpenCV does, resize it with its aspect ratio kept so that its longest side is 512 pixels, with bilinear interpolation, centre it on a black square of 512 pixels, give it as batch, channels, height and width, with values from 0 to 255, the normalization being inside the model; the tile keys say none because the run does not cut its images into tiles. On the right, the three resizes the contract can describe: stretch, keep_ratio and tiles. If a run uses an input the contract cannot describe, the export stops before writing any file, and a test rebuilds the inputs of a photo from the contract alone and checks them pixel for pixel against the training preprocessing.
